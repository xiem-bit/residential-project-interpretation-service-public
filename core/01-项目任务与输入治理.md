# 项目任务与输入治理

## 1. 先建立轻量项目合同

项目合同至少锁定：任务 ID、任务模式、业务问题、首要受众、使用场景、商机阶段、成果形态、项目身份、事实截止点、授权材料、明确不启用内容、当前有效裁定和被覆盖判断。

多期、多宗地、备案名与推广名并存时，项目身份必须说明它们之间的证据关系。相同数字、相邻地块或同品牌不能自动建立关联。

## 2. 原始输入分工

| 输入 | 可以贡献 | 不可以冒充 |
| --- | --- | --- |
| 正式／甲方资料 | 项目、产品、权益、时间、正式表达 | 客户真实选择或竞争裁定 |
| 顾问稿／既有成果 | 竞争场域、章节逻辑、战略压缩、客户语言 | 当前动态事实或独立系统发现 |
| 客户声音／选择事件 | 替代、比较标准、筛选、否决、抗性、反例 | 总体统计或普遍共识 |
| 公开／机构数据 | 市场、供应、价格、传播与客户语言线索 | 本案定位、直接竞品或超级竞争力最终裁定 |
| 行业案例 | 解题机制、表达、反例 | 当前项目事实、配置、价格、客群或结果 |

真实交付优先复用已有授权成果，不为制造“独立研究”而忽略真实输入。公开教程和黄金参考用于学习方法、结构与取舍，不得替代当前项目输入。

## 3. 事实、判断、假设和缺口

每条关键输入登记为：

- `fact`：材料直接支持；
- `limited_observation`：只在样本或场景内成立；
- `business_judgment`：由多项输入推导；
- `working_assumption`：为继续生产而暂用；
- `gap`：缺失且可能改变结论；
- `conflict`：来源不一致；
- `cannot_infer`：现有信息不能支持该断言。

同一数值出现差异时，不隐藏冲突。真实任务按当前有效正式值或业务 Owner 裁定；教程只演示如何保留冲突和影响。

## 4. 上游任务最小充分

只补会改变项目身份、竞争边界、购买任务、核心主张、SC 或项目承接的信息。任务必须说明判断缺口、用途、对象、时点、范围、证据职责、接受模式、质量／数量／多样性条件、每条冻结查询的执行下限、停止线、Owner 和回传格式。

第一轮回传后先检查业务充分性，不用“已执行查询”代替“证据够用”。上游可以提出增量批次，住宅生产 Owner 独立决定是否授权；每轮保留边际信息增益、负命中、冲突、gap和停止原因。上游只返回证据、变化与状态，不替住宅生产 Owner 裁定直接竞品或 SC；`fulfilled`不等于下游`accepted`。证据够用或继续检索无增益时标记`stop_search`，不因渠道仍可继续而无界扩搜。

## 5. 输入冻结

进入语义冻结前，记录输入清单、事实截止点、关键缺口处置、明确排除资料和冻结版本。冻结不表示事实永不变化，只表示下游本轮消费同一版本；后续变化进入变更登记。
