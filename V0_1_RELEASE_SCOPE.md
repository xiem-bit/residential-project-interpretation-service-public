# v0.1 RC1 release scope (historical, immutable)

> Current classification: this fixed release demonstrates downstream contracts,
> platform round-trips and carrier QA after a semantic core has already been supplied.
> It does not evaluate discovery of a residential competition strategy from raw inputs.
> The complete production-path candidate is defined by `V0_2_RELEASE_SCOPE.md`.

Status: `public_rc_authorized / local_end_to_end_verified / workbuddy_pending`

## Final design goal

A colleague or agent with no private project history and no Codex machine runtime can
understand the method, install the public dependencies, complete one fictional
residential-project workflow, route platform-specific production to available skills,
and verify the returned deliverables without using real customer assets.

## Responsibility boundary

| Layer | v0.1 responsibility |
| --- | --- |
| Public core | Method and input contracts, schemas, runnable validators, structural PPTX operations, business gates, OOXML safety, static-package QA, acceptance interfaces and honest gap output |
| Platform adapter | High-quality PPT generation, page design, visual assembly and rendering; the adapter may be Codex, WorkBuddy, another agent platform or a human team |
| Private authority repository | Real projects, customer materials, golden implementations, high-state production runtimes, publishing profiles and unrestricted Codex-native production |

Formal presentation visual fidelity is an adapter acceptance responsibility. The public
core must define what evidence the adapter returns, but it does not bundle or reproduce
a final presentation renderer.

## Single RC1 fictional flow

1. Read `START_HERE` and run the environment check.
2. Load a fully fictional client brief, evidence bundle and explicit gaps.
3. Validate the research and Product 3 business contracts.
4. Produce a platform-neutral Product 3 presentation production package.
5. Route presentation generation to an available platform adapter.
6. Validate the returned PPTX with business gates and structural package QA.
7. Load the same approved semantic core into a minimum generic Product 5 shell.
8. Build and validate a relative-path static bundle.
9. Run delivery checks and emit a final receipt that separates completed work from gaps.

The fixture uses frozen synthetic evidence. Live public-channel collection is not needed
to prove the RC1 cold start; upstream integration is represented by a pinned contract and
can be tested separately.

## Must finish before v0.1 RC1 acceptance

- one platform-neutral `START_HERE`, environment check and unified verification entry;
- one complete fictional project with inputs, expected intermediate contracts and final
  acceptance assertions;
- public method, schema and capability-routing instructions that do not assume Codex;
- relative-path UE static-bundle manifest creation and verification;
- a minimum Product 5 generic shell with no real project names, images, routes, domains,
  QR codes or publishing configuration;
- a presentation adapter contract that accepts the production package and returns an
  editable PPTX, preview or equivalent visual evidence, object/page mapping and gaps;
- a single fictional end-to-end receipt with no real assets, credentials, absolute paths
  or undocumented manual steps.

The browser-bound web-review implementation is not a default RC1 dependency. Static
bundle integrity, offline policy, semantic continuity and documented platform visual
review are sufficient for the fictional flow. A browser-review component enters RC1
only if an independent cold start proves that the delivery cannot be completed without it.

## Should finish when low cost

- generic A4 PDF rendering, only if the fictional flow needs a printable report;
- a WorkBuddy manifest after the platform-neutral local flow passes;
- compatibility checks against the pinned public-information upstream contract.

## Deferred from the first public release

- Grist and any specific visual assembly console;
- bundled formal PPT rendering or reproduction of Codex Presentations;
- cloud servers, SSH profiles, temporary publishing and account state;
- real project Product 5 source, images, QR codes and golden implementation assets;
- live public-channel collection as a cold-start prerequisite;
- full `delivery_full` Product 5 production.

## RC1 acceptance criteria

- a fresh directory installs with documented standard Python and Node dependencies;
- the entire fictional flow runs from one public entrypoint without private repository
  reads or Codex-only environment variables;
- another agent can discover required capabilities and either use its own skill or emit
  a contract-shaped gap instead of claiming unsupported completion;
- public validators accept the expected fixture and reject broken contracts, unsafe PPTX
  packages, absolute paths and incomplete static bundles;
- the final receipt separates method/structure validation, platform production evidence,
  local cold-start status and unverified cross-machine status;
- the package contains no real project, customer, credential, internal server, private Git
  history or private holdout material.

## Anti-expansion rules

- Do not improve PPT aesthetics or build another presentation renderer in the public core.
- Do not revisit the recorded `image-size` exception before `2026-09-25` unless a reopen
  condition in `DEPENDENCY_EXCEPTIONS.json` occurs.
- Do not promote a B-class component unless the fictional flow exposes a concrete missing
  capability that it closes.
- Treat static bundle, Product 5 shell and capability routing as workstreams inside one
  RC1 outcome, not separate approval milestones.
- Grist and A4 PDF cannot block RC1 unless the fictional acceptance flow proves they are
  necessary.

## Implementation order inside the single RC1 outcome

1. Add `START_HERE`, the fictional project skeleton and the unified receipt contract.
2. Extract only the static-bundle functions exercised by that fixture; route formal
   browser visual review to the selected platform.
3. Extract the minimum Product 5 shell and replace all project-specific content.
4. Add the platform adapter contract and a test double; do not add a renderer.
5. Run the full local clean-directory cold start and repair only observed blockers.
6. Decide from the completed flow whether A4 PDF or a WorkBuddy-specific manifest belongs
   in v0.1.
